# C4. 배포 열쇠: 서버에 들어오는 SSH 키

지금 하는 일: 배포 잡이 VPS에 접속해서 helper를 부르는 마지막 단계를 봅니다. 이 단계의 열쇠가 새거나 악용되면 서버가 직접 위험해집니다.

## 상황

Jenkins로 배포할 때는 Jenkins가 서버 안에서 `docker.sock`을 들고 일했습니다(`vps-infra`의 `jenkins/compose.yml`에서 `/var/run/docker.sock`을 마운트). `docker.sock`을 쥔 프로세스는 컨테이너를 만들어 서버의 `/` 전체를 마운트할 수 있어서 사실상 root입니다.

이번 구조에서는 GitHub 서버의 배포 잡이 SSH로 VPS에 들어옵니다. 접속 계정이 docker 그룹에 속해 있으면 같은 문제가 생깁니다. 계정을 얻은 사람이 `docker run -v /:/host …` 한 줄로 서버 전체를 읽고 씁니다. 그래서 배포 계정에는 docker 권한을 주지 않고, 배포라는 일 하나만 하는 열쇠를 만듭니다.

## 막는 장치

순서가 실제 연결 순서라서 번호를 붙입니다.

1. 접속 경로. 배포 잡은 Tailscale 임시 노드로 들어오고, ACL이 그 노드에서 서버의 22번 포트만 허용합니다. Tailscale 자격은 Environment 시크릿에 둡니다. 저장소 시크릿에 두면 모든 잡이 tailnet에 들어올 수 있습니다.
2. 열쇠가 할 수 있는 일. 서버의 `authorized_keys`에 이 열쇠를 등록할 때 `command="helper 경로"`를 붙이면, 이 열쇠로 어떤 명령을 요청해도 helper만 실행됩니다. 여기에 `restrict`를 붙입니다. `command=`만 있으면 포트 포워딩, agent 포워딩, pty가 남아서, 열쇠로 터널을 열어 서버 안쪽(127.0.0.1)에서만 열려 있는 DB나 관리 서비스에 닿을 수 있습니다. `restrict`가 그것들을 한꺼번에 끕니다. `authorized_keys`는 root 소유여야 합니다. 배포 계정이 고칠 수 있으면 제한을 지웁니다.
3. helper가 받는 인자. 클라이언트가 요청한 명령은 `SSH_ORIGINAL_COMMAND` 환경변수로 helper에 들어옵니다. 이 문자열을 검증 없이 셸에 쓰면 인젝션이 됩니다. 그래서 환경은 `dev`와 `prod` 둘만, digest는 `sha256:` 뒤에 소문자 16진수 64자리만 받고, 그 밖의 옵션이나 추가 인자는 거부합니다.
4. helper 자체. root 소유의 고정 스크립트라서 배포 계정이 고칠 수 없고, 쓰는 compose도 관리자가 서버에 설치한 것입니다. CI가 compose를 보내서 실행하게 하면, `main`에 들어간 compose 한 줄(`privileged: true`)이 곧 서버 root가 됩니다.
5. Tailscale SSH. 서버에서 `tailscale up --ssh`가 켜져 있으면, tailnet 쪽에서 오는 22번 접속을 tailscaled가 가로채서 처리합니다. 그러면 2번의 `authorized_keys`와 `command=`가 적용되지 않습니다. 그래서 끄고, 꺼졌는지 확인합니다.
6. 상태 저장 위치. 환경 잠금 파일과 "현재 릴리스" 기록은 root 소유 디렉터리에 둡니다. 배포 계정이 쓸 수 있는 곳(`/tmp` 등)에 두면, 기록을 바꿔서 다운그레이드 가드를 풀거나 심볼릭 링크로 root가 엉뚱한 파일을 쓰게 만들 수 있습니다.
7. 롤백. helper는 현재보다 오래된 릴리스로의 배포를 막습니다. 그러면 장애 때 직전 정상 버전으로도 돌아가지 못합니다. 그래서 그 환경에 과거에 성공 배포된 릴리스로의 롤백만 예외로 허용합니다.

## 그래도 남는 구멍

- 환경별 SSH 키와 tailnet 접근이 둘 다 유출되면, 공격자는 출처 증명이 유효한 이미지 중 아무거나 골라 배포할 수 있습니다. 대응은 키 폐기와 교체 런북입니다.
- prod 승인(Environment 클릭)은 같은 사람이 합니다. 이 승인은 워크플로가 침해된 경우를 막습니다. 사용자님 계정이 침해된 경우는 막지 못합니다.
- 한 VPS에 dev와 prod가 같이 있어서 Tailscale 태그로는 둘이 갈리지 않습니다. 한 서버가 한 노드이기 때문입니다. 분리는 환경별 키와 Environment가 맡습니다.

## 직접 해보기

로컬 bash로 helper의 인자 검사만 짜 봅니다. `SSH_ORIGINAL_COMMAND` 값을 읽어서 `PASS` 또는 `FAIL`만 출력하는 스크립트입니다. 다음 입력을 모두 시험합니다.

- 정상: `dev sha256:` 뒤에 소문자 16진수 64자리
- `prod; rm -rf /`
- `dev -v sha256:…`
- 대문자 16진수
- 여러 줄 입력(첫 줄은 정상, 둘째 줄에 다른 명령)

여러 줄 입력이 통과하면, 검사가 첫 줄만 본다는 뜻입니다.

## 확인 질문

`command=`만 붙인 열쇠로 어떻게 서버의 127.0.0.1 서비스에 닿을 수 있나요? `restrict`가 그 경로를 어떻게 막나요?
