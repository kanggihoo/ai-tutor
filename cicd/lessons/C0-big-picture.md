# C0. 큰 그림

지금 하는 일: ci-cd-lab에서 정한 보안 결정들이 파이프라인의 어디에 붙는지 한 장으로 봅니다. 이 흐름을 알아야 C1부터 나오는 결정이 어떤 구멍을 막는지 보입니다.

## 코드가 서버에 올라가는 길

1. 사용자님이 branch에서 코드를 고치고 PR을 올립니다.
2. GitHub Actions가 PR에 검사를 돌립니다(gitleaks, govulncheck 등). 이 검사들의 결과를 하나로 묶은 잡이 `gate`입니다.
3. `gate`가 통과해야 PR을 `main`에 squash 병합할 수 있습니다.
4. `main`에 병합되면 `main` 전용 워크플로가 `be`, `fe`, `migrate` 이미지 세 개를 GitHub 서버에서 빌드해서 `ghcr.io/kanggihoo/ci-cd-lab/` 아래에 `sha-<커밋>` 태그로 올립니다. 이때 GitHub이 "이 워크플로가 이 커밋에서 만들었다"는 서명된 증명(출처 증명)을 이미지에 붙입니다.
5. 세 이미지의 digest(내용 지문)와 소스 커밋을 묶은 `release.json`이 만들어집니다.
6. 배포 잡이 VPS에 SSH로 접속해서 서버에 설치된 helper를 부르고 digest를 넘깁니다. helper는 증명을 다시 확인한 뒤 `lab-dev` 또는 `lab-prod`를 그 이미지로 띄웁니다.

## Jenkins와 다른 점

Jenkins는 서버 안에서 저장소를 받고, 빌드하고, 배포까지 합니다. 이 구조에서는 빌드를 GitHub 서버에서 하고, 서버는 완성된 이미지의 digest만 받습니다. 서버가 믿어야 하는 대상이 "빌드 환경 전체"에서 "서명된 이미지 하나"로 줄어듭니다.

## 공격자의 시선

이 저장소는 공개라서 코드, 워크플로 파일, 로그를 누구나 읽을 수 있다고 가정합니다. 그 상태에서 prod 서버에 닿으려는 사람은 길의 세 군데를 노립니다. 입구(2~3단계), 중간(4~5단계), 끝(6단계)입니다.

택배 물류센터로 생각하면 쉽습니다. 입구에는 검수대가 있고(`gate`), 중간에는 포장 구역과 송장이 있고(게시 경계, 출처 증명), 끝에는 배송 기사가 가진 열쇠가 있습니다(배포 열쇠). 공격자는 검수대를 속이거나, 포장 구역에 몰래 들어가 상자를 바꾸거나, 기사의 열쇠를 훔치면 됩니다.

각 레슨은 이 길의 한 구간을 맡습니다. C1이 입구, C2와 C3이 중간, C4와 C5가 서버 쪽 끝, C6이 길 전체에 걸친 로그, C7이 정리입니다.

## 지키는 것

prod 서버와 그 안의 데이터, 그리고 저장소와 서버에 둔 비밀(SSH 키, 토큰)입니다.

## 직접 해보기

종이에 위 6단계를 그리고, 각 화살표마다 "여기서 공격자가 할 수 있는 일"을 한 줄씩 적어 봅니다. 틀려도 되고, C7에서 다시 채웁니다.
