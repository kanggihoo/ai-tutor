# C6. 로그 위생: 공개 로그에 무엇이 찍히나

지금 하는 일: 저장소가 공개라서 Actions 로그도 누구나 읽을 수 있다고 가정하고, 로그에 찍히면 안 되는 것을 정리합니다.

## 상황

배포 잡이 Tailscale 임시 노드로 접속하는 중에 SSH가 실패했다고 합시다. SSH는 "Permission denied" 메시지와 함께 접속하려던 주소(tailnet의 `100.x.y.z`)를 출력합니다. 이 주소는 GitHub에 비밀로 등록한 값이 아니라서 로그에 그대로 찍힙니다.

GitHub의 마스킹은 비밀로 등록한 값이 로그에 나오면 `***`로 바꿔 주는 기능입니다. 값이 정확히 같은 문자열일 때만 동작합니다. 실행 중에 알게 되는 tailnet 이름이나 IP는 등록된 값이 아니라서 가려지지 않습니다. 비밀을 조금 바꾼 형태(base64나 URL 인코딩)도 가려지지 않을 수 있습니다.

배포 출력도 문제입니다. helper가 `docker compose`를 실행하면 컨테이너 이름, 네트워크 이름, 내부 주소가 출력됩니다. 마이그레이션이 실패하면 출력에 SQL이나 행 데이터가 섞일 수 있습니다. SSH가 이 출력을 배포 잡으로 그대로 가져와 로그에 찍습니다.

## 막는 장치

무엇을 비밀로 볼지부터 좁힙니다. 사설 IP, tailnet 이름과 주소, 서버 내부 경로는 비밀입니다. compose 파일에 적힌 컨테이너 내부 포트(예: 8080), 환경 이름(`lab-dev`), 공개 호스트명(`lab.kkh-hub.tech`)은 이미 공개 저장소나 인증서 투명성 로그에 있어서 비밀이 아닙니다. 공개된 것을 숨기려 들면 첫날부터 규칙을 어기게 됩니다.

실행 중에 알게 되는 비밀 값은 쓰기 전에 `::add-mask::<값>`으로 등록합니다. helper는 `PASS` 또는 `FAIL`과 digest만 출력하고, 상세 로그는 서버에만 남깁니다.

공개 로그에는 env 값의 해시도 남기지 않습니다. 짧거나 예측하기 쉬운 비밀은, 공격자가 후보를 해시해서 로그의 해시와 비교하면 맞힐 수 있습니다.

## 그래도 남는 구멍

로그를 자동으로 스캔하는 도구는 이번 반복에 두지 않습니다. 저장소와 이미지에 대한 비밀 검사는 gitleaks와 이미지 스캔(D-6)이 합니다. 로그에 무엇이 찍혔는지는 사람이 확인합니다.

## 직접 해보기

GitHub Actions 안에서만 재현되는 내용이라 지금은 설명만 합니다. 2단계에서 워크플로가 생기면, 등록하지 않은 값을 `echo`한 로그와 `::add-mask::`를 건 뒤의 로그를 비교해 봅니다.

## 확인 질문

등록하지 않은 tailnet IP가 로그에 `***` 없이 찍히는 이유와, 그걸 막으려면 언제 무엇을 해야 하는지 설명해 보세요.
