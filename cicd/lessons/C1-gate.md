# C1. gate: PR이 main으로 들어가는 입구

지금 하는 일: PR이 `main`에 합쳐지기 전에 거치는 검사 구조를 봅니다. 파이프라인의 첫 번째 방어선입니다.

## 상황

FE 파일만 고친 PR을 올렸다고 합시다. Go 검사(govulncheck 등)는 돌릴 필요가 없으니 건너뛰게 만들고 싶습니다. 구현 방법은 두 가지이고, GitHub은 이 둘을 서로 다르게 취급합니다.

첫째, 워크플로 안의 잡에 `if` 조건을 걸어 건너뛰는 방법입니다. 건너뛴 잡은 "성공"으로 표시됩니다. 이 잡이 필수 체크라면 검사를 한 번도 하지 않았는데 병합 버튼이 열립니다.

둘째, 워크플로 파일 전체에 경로 필터(`paths:`)를 걸어서 해당 경로가 안 바뀌면 워크플로가 아예 시작되지 않게 하는 방법입니다. 이때 필수 체크는 결과가 오지 않아서 "대기 중"에 머물고, 병합이 영원히 막힙니다.

첫째는 검사 없이 병합되는 구멍이고, 둘째는 병합이 막히는 불편입니다.

## 막는 장치

개별 검사를 필수 체크로 걸면 위 두 경우가 모두 문제가 됩니다. 그래서 필수 체크는 따로 만든 잡 하나, `gate`에만 겁니다.

`gate`는 모든 검사 잡이 끝난 뒤에 도는 잡입니다. 각 잡의 결과를 읽어서 하나라도 success가 아니면(실패, 건너뜀, 취소 모두 포함) 스스로 실패합니다. 경로 필터는 개별 잡을 돌릴지 말지만 정하고, `gate`는 항상 돕니다. 검사가 늘거나 줄어도 필수 체크 이름은 `gate`로 같아서 ruleset을 고칠 일이 없습니다.

`gate`에는 `if: always()`를 붙여야 합니다. 앞선 잡이 실패하면 뒤따르는 잡은 기본적으로 건너뛰어지는데, 건너뜀은 성공으로 표시됩니다. 그러면 `gate`가 실패해야 할 때 오히려 통과합니다.

두 번째 구멍은 이름입니다. 체크 이름은 문자열이라서, 다른 GitHub App이나 토큰이 `gate`라는 이름으로 성공 상태를 보내면 같은 체크로 취급됩니다. 그래서 ruleset에서 필수 체크의 출처를 GitHub Actions로 고정합니다(D-4, D-15).

## 그래도 남는 구멍

같은 저장소의 branch에서 올린 PR은 그 PR 쪽 버전의 워크플로 파일로 돕니다. PR이 `gate` 잡의 내용을 `exit 0`으로 바꾸면 그 `gate`가 통과합니다. 팀이라면 `.github/` 폴더의 변경을 다른 사람이 리뷰하도록 막지만, 1인 운영이라 막을 사람이 없습니다. 이 구멍은 알면서 감수합니다(D-4).

1단계에서 일부러 이 PR을 올려서 통과하는 것을 직접 확인합니다(D-16).

## 직접 해보기

지금은 설명만 합니다. ci-cd-lab 1단계에서 워크플로가 생기면 두 가지를 해 봅니다. 필수 체크를 일부러 실패시켜 병합이 막히는지 보고, `gate`를 `exit 0`으로 고친 PR이 통과하는지 봅니다.

## 확인 질문

FE만 바뀐 PR에서 Go 검사 잡이 건너뛰어졌을 때, 그 잡이 필수 체크라면 병합은 막히나요, 열리나요? 워크플로 전체가 경로 필터로 시작하지 않은 경우와 비교해서 말해 보세요.
