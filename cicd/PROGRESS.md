## 약점 (Weak spots)
- CI 검사 실행·결과 전달과 GitHub의 필수 검사 규칙 구분: 설명 후 이해 확인. 결과 누락 시 병합 차단은 힌트 없는 정답 1회. 졸업 전.
- `gate` 결과로 병합을 막는 주체는 GitHub 규칙이라고 정답. 순차·병렬 실행과 Jenkins·GitLab에서의 같은 역할을 질문함. `gate`는 이 프로젝트의 job 이름이며 공통 개념과 구분해 설명.
- `gate` 판단: 테스트 실패가 하나 있으면 최종 실패라고 힌트 없는 정답 1회. 건너뜀은 변경 파일 기반의 의도적 생략으로 해석함. 이번 순차 예시는 앞 job 실패에 따른 의존 job의 건너뜀이므로 두 원인 구분 필요.
- C2 개념 설명 진행: 태그와 digest 구분, layer의 해시를 포함한 manifest의 바이트에서 digest 계산, 이미지에 반영된 변경이 digest를 바꾼다는 점을 이해했다고 응답. 독립 확인 문제는 아직 미실시. CD에서 검사 후 배포 여부를 결정한다는 사용자 이해 확인. 관리자 탈취로 정상 절차를 거친 악성 이미지까지 출처 확인으로 막지는 못함을 설명.
- PR에서 CI 설정을 고쳐 `gate`를 무조건 통과시키는 상황을 이해하고 리뷰 승인 강제를 방어책으로 제안함. 규칙 변경 권한까지 가진 1인 관리자 계정은 승인 규칙만으로 완전히 막지 못한다고 정답 1회. 졸업 전.

## 이번 수업 기록 (2026-11-06)
- C0~C4를 대화로 진행. 전 레슨 완료나 약점 졸업으로 처리하지 않음.
- CI: 결과를 전달하는 것과 GitHub 규칙으로 병합을 막는 것은 별개. Jenkins·GitLab에서도 같은 역할을 구성 가능. `gate`는 이 프로젝트의 최종 판정 job 이름이며 필수 구조는 아님.
- 건너뜀: 앞 job 실패에 따른 생략과 변경 파일 조건에 따른 의도적 생략을 구분. 별도 outputs로 검사 필요 여부를 전달할 수 있다는 사용자 제안 확인.
- 관리자 탈취: 병합 규칙을 수정할 수 있는 계정까지 탈취되면 해당 규칙만으로 막지 못함. CD에서 추가 검증해도 정상 제작 경로를 거친 악성 코드 자체를 판별하는 것은 아님.
- 이미지: 태그는 재사용될 수 있음. digest는 내용 기반 식별값. GHCR이 이미지를 보관하고, 배포 기록에는 이미지 주소·digest·소스 commit 등을 남겨 재배포·롤백에 사용. 해당 이미지도 보존돼 있어야 함.
- 출처 증명: 생성 Action을 설정해 제작 정보·서명·인증서를 묶어 저장하고, 배포 시 허용된 저장소·워크플로·ref·commit과 대조. 인증기관의 서명과 제작자의 서명이 서로 다른 대상을 보호한다는 설명에서 어려움이 있었음. 사용자는 말로 반복하지 말고 실제 결과물을 보며 확인하기를 원함. 로컬 원본·변조·다른 키 검증 비교와 실제 증명 묶음 확인을 실습으로 보류.
- C4: `helper`는 표준 배포 용어가 아니라 프로젝트의 이름. 사용자 요청에 따라 앞으로 대화에서는 **배포 스크립트**로 통일. 서버에 미리 설치한 배포 스크립트만 실행하도록 `authorized_keys`에 `command=` 설정. `restrict`는 포트 포워딩 등 추가 기능 제한.
- SSH 키 쌍은 서버에서 생성할 필요 없음. 신뢰하는 PC 등에서 생성 가능. 공개키는 서버의 `authorized_keys`에 제한과 함께 등록하고, 개인키는 CD가 사용할 GitHub Actions secret에 보관. 여기까지 설명 후 사용자가 기록 요청.
- 정본 결정 로그가 기록된 경로에 없어 D 항목 최신 상태는 미확인. 기존 레슨 자료로 진행했으며 정본을 수정하지 않음.
- 공식 문서로 확인: GitHub 필수 검사·needs의 실패/건너뜀 동작, digest 기반 pull, 증명 생성 Action·저장 옵션, `gh attestation verify`의 제작 경로 제한과 조회 방식, OpenSSH 키별 제한. 실제 명령 실행과 서버 검증은 미실시.
- 회고: 요청 예정. 사용자 결론은 회고 통과 전 기록하지 않음.

## 이번 수업 기록 (2026-11-10~11)
- 정본 D-20과 ADR 0001을 원래 경로에서 확인. 배포 계정의 Docker 직접 접근 금지와 root 소유 고정 배포 스크립트·Compose 사용 방향은 기존 레슨과 일치. 정본은 수정하지 않음.
- 복습: 사용자는 forced command가 요청 명령을 거부하는지 지정 스크립트를 실행하는지 두 후보를 말함. 지정 스크립트 실행으로 설명했으며 힌트 없는 정답으로 집계하지 않음. 제한은 키 생성 시점이 아니라 서버 공개키 등록 시점에 붙임.
- `SSH_ORIGINAL_COMMAND`를 eval로 실행하면 지정 스크립트 안에서 임의 명령 실행을 다시 허용하게 됨을 설명. 사용자는 eval이 있으면 입력 명령이 실행된다고 답함. 입력 검증과 데이터로만 사용하는 방식은 설명했고 독립 확인은 미실시.
- eval 별도 설명: 문자열을 현재 셸의 코드로 해석·실행. `$()`는 명령 출력을 가져오고 eval은 그 출력을 코드로 실행. ssh-agent 출력은 환경변수 설정 코드이며 출력만으로 현재 셸에 적용되지 않음. 사용자가 python -c와 연결해서 이해를 표현함.
- 스크립트 보호: chown으로 root 소유, chmod로 배포 계정 쓰기 금지. 소유자가 배포 계정이면 chmod로 쓰기를 다시 허용할 수 있음. 상위 디렉터리 쓰기도 금지해야 교체를 막음. 사용자 이해 응답, 독립 퀴즈 미실시.
- Docker: `-v /:/host`는 서버 `/`를 컨테이너의 임의 경로 `/host`에 bind mount. 복사본이 아니라 같은 서버 파일이며 기본 읽기·쓰기. 사용자는 mount인지, /host가 특별한 경로인지 차례로 확인함.
- 핵심 권한 연결: 일반적인 rootful Docker에서 user namespace 격리가 없다면 Docker를 자유롭게 실행하는 사용자는 `--user 0`과 호스트 bind mount로 서버 파일을 root 권한으로 수정할 수 있음. mount가 권한을 덮어쓰는 것은 아님. 이미지의 USER도 실행자가 덮어쓸 수 있음. rootless/user namespace에서는 컨테이너 root가 곧 서버 root는 아니므로 일반화 금지.
- 배포 계정에는 Docker 그룹·소켓 권한을 주지 않고, sudoers로 고정 배포 스크립트만 높은 권한으로 실행하도록 허용하는 방식을 설명. **root 소유와 root로 실행은 별개.** 실제 sudoers 규칙·인자 정책·서버 설정은 아직 확인하거나 작성하지 않음.
- Compose 보호: root 소유 파일 및 상위 디렉터리에 배포 계정 쓰기 금지. 스크립트 안에 Compose 절대 경로를 고정하며 사용자가 다른 경로를 지정하게 하지 않음. Compose가 참조하는 다른 파일·환경변수까지 보호해야 하는 범위는 다음에 설명할 것.
- 전부 설명만 진행. Docker·서버 명령 실행이나 외부 전송 없음. C4 완료·약점 졸업으로 처리하지 않음.
- 설명 피드백: 사용자는 전제 생략과 모호한 질문에 강하게 불만을 표시함. 계정 권한 → Docker daemon 권한 → 컨테이너 프로세스 권한 → 서버 파일 접근을 생략하지 말 것. 질문은 공격자가 이미 가진 권한과 가능한 행동을 명시하고 한 번에 하나만 묻기.
- 회고: 요청 예정. 사용자 결론은 통과 전 기록하지 않음.

## 다음 단계
1. **Docker 권한과 sudo·Compose 보호에서 바로 이어가기.** 시작 문구: "지난번엔 배포 계정에 Docker 직접 권한을 주지 않고, 고정 배포 스크립트만 sudo로 실행하게 하는 구조까지 봤어요. 다음은 그 허용 범위를 실제로 어떻게 제한하는지입니다."
2. 짧은 복습 하나: "배포 계정은 deploy.sh만 sudo로 실행할 수 있고 sudo docker는 거부됩니다. 그런데 deploy.sh가 읽는 compose.yml은 배포 계정이 수정할 수 있습니다. 이때 어떤 설정을 넣어 서버 파일에 접근할 수 있을까요?" 이미 설명한 mount 예를 전제로 질문하고 모르면 힌트부터. 횟수는 힌트 없는 정답만 기록.
3. D-20·ADR 0001 및 실제 코드 존재 여부를 확인한 뒤 sudoers의 고정 실행 경로·인자 제한과 스크립트 내부 검증을 구분해 설명. 앞선 sudo 예시는 개념 설명이며 실제 정책이 확인된 것으로 취급하지 않기. 사용자 임의 Docker 옵션·Compose 경로를 받지 않는 이유부터 한 개념씩.
4. Compose 자체뿐 아니라 참조하는 .env·추가 Compose 파일·실행 파일과 경로의 수정 권한이 왜 중요한지 구체적인 한 사례로 설명. Docker rootful/rootless·UID 매핑은 질문이 있을 때 필요한 범위로만.
5. 이후 C4 나머지: 환경·digest 검사 실습, restrict의 포워딩 차단, Tailscale SSH, 상태 기록 보호·롤백. Tailscale 동작은 공식 문서 확인 후 설명.
6. 실습은 사용자와 시점이 맞을 때 `~/Desktop/cicd-practice/`에서. Docker 설치 여부 먼저 확인. 실제 GitHub·서버 작업과 외부 전송은 하지 않음. C3는 실제 파일 비교 실습으로 보류 유지. C0부터 다시 시작하지 않음.
