## 약점 (Weak spots)
- CI 검사 실행·결과 전달과 GitHub의 필수 검사 규칙 구분: 설명 후 이해 확인. 결과 누락 시 병합 차단은 힌트 없는 정답 1회. 졸업 전.
- `gate` 결과로 병합을 막는 주체는 GitHub 규칙이라고 정답. 순차·병렬 실행과 Jenkins·GitLab에서의 같은 역할을 질문함. `gate`는 이 프로젝트의 job 이름이며 공통 개념과 구분해 설명.
- `gate` 판단: 테스트 실패가 하나 있으면 최종 실패라고 힌트 없는 정답 1회. 건너뜀은 변경 파일 기반의 의도적 생략으로 해석함. 이번 순차 예시는 앞 job 실패에 따른 의존 job의 건너뜀이므로 두 원인 구분 필요.
- C2 개념 설명 진행: 태그와 digest 구분, layer의 해시를 포함한 manifest의 바이트에서 digest 계산, 이미지에 반영된 변경이 digest를 바꾼다는 점을 이해했다고 응답. 독립 확인 문제는 아직 미실시. CD에서 검사 후 배포 여부를 결정한다는 사용자 이해 확인. 관리자 탈취로 정상 절차를 거친 악성 이미지까지 출처 확인으로 막지는 못함을 설명.
- PR에서 CI 설정을 고쳐 `gate`를 무조건 통과시키는 상황을 이해하고 리뷰 승인 강제를 방어책으로 제안함. 규칙 변경 권한까지 가진 1인 관리자 계정은 승인 규칙만으로 완전히 막지 못한다고 정답 1회. 졸업 전.

## 이번 수업 기록 (2026-11-06)
- C0~C4를 대화로 진행. 전 레슨 완료나 약점 졸업으로 처리하지 않음.
- CI: 결과를 전달하는 것과 GitHub 규칙으로 병합을 막는 것은 별개. Jenkins·GitLab에서도 같은 역할을 구성 가능. `gate`는 이 프로젝트의 최종 판정 job 이름이며 필수 구조는 아님.
- 건너뜀: 앞 job 실패에 따른 생략과 변경 파일 조건에 따른 의도적 생략을 구분. 별도 outputs로 검사 필요 여부를 전달할 수 있다는 사용자 제안 확인.
- 관리자 탈취: 병합 규칙을 수정할 수 있는 계정까지 탈취되면 해당 규칙만으로 막지 못함. CD에서 추가 검증해도 정상 제작 경로를 거친 악성 코드 자체를 판별하는 것은 아님.
- 이미지: 태그는 재사용될 수 있음. digest는 내용 기반 식별값. GHCR이 이미지를 보관하고, 배포 기록에는 이미지 주소·digest·소스 commit 등을 남겨 재배포·롤백에 사용. 해당 이미지도 보존돼 있어야 함.
- 출처 증명: 생성 Action을 설정해 제작 정보·서명·인증서를 묶어 저장하고, 배포 시 허용된 저장소·워크플로·ref·commit과 대조. 인증기관의 서명과 제작자의 서명이 서로 다른 대상을 보호한다는 설명에서 어려움이 있었음. 사용자는 말로 반복하지 말고 실제 결과물을 보며 확인하기를 원함. 로컬 원본·변조·다른 키 검증 비교와 실제 증명 묶음 확인을 실습으로 보류.
- C4: `helper`는 표준 배포 용어가 아니라 프로젝트의 이름. 사용자 요청에 따라 앞으로 대화에서는 **배포 스크립트**로 통일. 서버에 미리 설치한 배포 스크립트만 실행하도록 `authorized_keys`에 `command=` 설정. `restrict`는 포트 포워딩 등 추가 기능 제한.
- SSH 키 쌍은 서버에서 생성할 필요 없음. 신뢰하는 PC 등에서 생성 가능. 공개키는 서버의 `authorized_keys`에 제한과 함께 등록하고, 개인키는 CD가 사용할 GitHub Actions secret에 보관. 여기까지 설명 후 사용자가 기록 요청.
- 정본 결정 로그가 기록된 경로에 없어 D 항목 최신 상태는 미확인. 기존 레슨 자료로 진행했으며 정본을 수정하지 않음.
- 공식 문서로 확인: GitHub 필수 검사·needs의 실패/건너뜀 동작, digest 기반 pull, 증명 생성 Action·저장 옵션, `gh attestation verify`의 제작 경로 제한과 조회 방식, OpenSSH 키별 제한. 실제 명령 실행과 서버 검증은 미실시.
- 회고: 요청 예정. 사용자 결론은 회고 통과 전 기록하지 않음.
