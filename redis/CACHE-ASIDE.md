# cache-aside와 버전·묘비 방식

버전·묘비 방식은 cache-aside에서 **무효화 후 옛 값이 다시 저장되는 문제**를 막는다. DB 변경과 Redis 반영 사이의 실패까지 해결하지는 못한다.

## 기본 cache-aside

- 조회 요청: Redis 조회 → cache 미스면 DB 조회 → 조회한 값을 Redis에 저장 → 응답.
- 변경 요청: DB 변경·commit → Redis의 해당 key를 `DEL`.
- DB가 원본이고 Redis는 조회를 빠르게 하기 위한 복사본이다.
- 버전은 DB 데이터 변경 시 증가한다. 조회하거나 Redis에 복사할 때 증가하지 않는다.

## 기본 방식에서 발생하는 문제

### 1. 옛 값 재삽입 — `1a-race`

1. A가 cache 미스로 DB에서 가격 100, v1을 읽고 멈춘다.
2. B가 DB를 가격 200, v2로 변경하고 commit한다.
3. B가 Redis key를 `DEL`한다.
4. A가 재개해서 읽어 둔 가격 100, v1을 Redis에 저장한다.

결과: DB는 v2인데 cache는 v1이다. 이런 옛 값을 stale data라고 부른다.

`DEL`로 버전 정보까지 사라졌으므로, 단순히 저장 직전에 버전을 비교하려 해도 비교할 기준이 없다.

### 2. 무효화 누락 — `1a-crash`

1. DB와 cache에 가격 100, v1이 있다.
2. B가 DB를 가격 200, v2로 변경하고 commit한다.
3. B의 프로세스가 `DEL` 전에 죽거나 Redis 명령이 실패한다.

결과: 기존 cache의 v1이 남는다. 기존 값은 남은 cache TTL 동안 반환될 수 있다.

## 버전·묘비로 개선하는 방법

### Redis 저장 형태

상품 하나당 key는 `product:1` 하나이며, value는 Hash다. 묘비용 key를 별도로 만들지 않는다.

| 구분 | `product:1`의 필드 | 조회 요청 처리 |
|---|---|---|
| 일반 cache | `price=100`, `v=1` | 가격을 반환 |
| 묘비 | `v=2`, `tomb=1` | 가격이 없으므로 DB 조회 |
| key 없음 | 없음 | DB 조회 |

`tomb`는 Redis 내장 기능이 아니라 우리가 정한 필드다. 가격은 지우되 **“v2보다 오래된 값은 저장하지 마”**라는 기록을 남긴 것을 묘비라고 부른다.

### 변경 요청 — `update()`

1. DB에서 가격 변경과 `version + 1`을 수행한다.
2. 같은 SQL의 `RETURNING version`으로 변경한 버전을 받는다.
3. DB commit 이후 Lua `INVALIDATE`를 실행한다.
4. Redis의 현재 버전보다 들어온 버전이 작으면 아무것도 바꾸지 않는다.
5. 그렇지 않으면 새 버전과 `tomb=1`을 기록하고 `price`를 제거한 뒤 묘비 TTL을 설정한다.

Redis에서 별도로 버전을 `INCR`하지 않는다. DB에서 받은 버전을 사용한다.

버전 검사는 변경 요청의 Redis 반영 순서가 뒤집혀도 v2가 이미 기록된 v3 기준을 낮추지 못하게 한다.

### 조회 요청 — `read()`

1. Redis에 값이 있고 `tomb`가 없으면 cache를 반환한다.
2. key가 없거나 `tomb`가 있으면 DB에서 가격과 버전을 조회한다.
3. Lua `FILL`에서 Redis의 현재 버전과 DB에서 읽은 버전을 비교한다.
4. DB에서 읽은 버전이 더 작으면 저장을 거절한다.
5. 같거나 크면 가격·버전을 저장하고 `tomb`를 제거한 뒤 cache TTL을 설정한다.

Redis에 버전 기준이 없으면 현재 구현은 버전을 0으로 취급한다.

### Lua를 사용하는 이유

`r.eval()`은 Lua 코드와 인자를 Redis 서버로 보내 실행한다. 버전 읽기·비교·저장을 수행하는 동안 다른 요청의 Redis 명령이 끼어들지 못한다.

Python에서 버전을 읽고 별도 명령으로 저장하면 두 명령 사이에 다른 요청이 값을 바꿀 수 있다.

이 원자성은 **Redis 안에서 다른 명령이 중간에 끼어들지 못한다는 뜻**이다. DB까지 하나의 트랜잭션으로 묶거나, Lua 실행 중 에러가 발생했을 때 앞선 쓰기를 자동 롤백한다는 뜻은 아니다.

## 해결하는 범위와 남는 한계

| 상황 | 버전·묘비의 효과 | 남는 문제 또는 대응 방향 |
|---|---|---|
| B의 묘비 기록 후 A가 옛 값을 저장 | 낮은 버전의 저장 거절 | A 자신에게 반환하는 옛 응답은 별개 |
| 늦은 v2 무효화가 v3 뒤에 도착 | 낮은 버전의 무효화 거절 | 모든 반영 경로가 검사를 지켜야 함 |
| DB commit 후 묘비 기록 전에 사망 | 해결 못 함 | TTL로 잔존 시간 제한, outbox·CDC로 전달 재시도 |
| 묘비 또는 일반 cache가 만료·eviction | 버전 기준을 잃음 | 늦은 요청의 저장을 거절할 근거가 사라짐 |
| A가 이미 v1을 읽음 | cache 저장만 거절 | 현재 코드는 A에게 v1을 그대로 응답 |
| 다른 코드가 버전 증가·Lua 검사를 우회 | 보호 못 함 | 모든 관련 변경·저장 경로가 같은 규칙을 따라야 함 |

## TTL과 timeout

| 구분 | 목적 |
|---|---|
| cache TTL | 저장한 가격을 언제까지 재사용할지 결정 |
| 묘비 TTL | 옛 버전을 거절하는 기록을 언제까지 보존할지 결정 |
| 요청 timeout | 특정 단계나 전체 요청의 대기·처리 시간을 제한 |

현재 코드의 묘비 TTL 60초는 **실험값**이며, 어떤 요청도 60초 뒤에 옛 값을 저장할 수 없다는 보장이 아니다.

FE가 응답 기다리기를 포기해도 서버 작업이 계속될 수 있다. 저장 직전에 애플리케이션에서 기한을 검사하더라도, 검사 직후 멈췄다가 나중에 저장하는 경우가 남는다. 요청 timeout 설정만으로 안전한 묘비 만료가 자동 보장되지는 않는다.

또한 묘비가 새 가격으로 교체되어도 그 cache의 TTL이 만료되면 버전 기준은 사라진다. 보존 조건은 묘비가 있는 동안에만 생각할 문제가 아니다.

묘비 기록에 실패했다면 묘비 TTL은 설정되지 않는다. 기존 cache가 남는 시간은 **기존 cache의 남은 TTL**이다. 옛 값이 나중에 재삽입되면 그 저장 시점부터 TTL이 다시 시작될 수 있다.

## outbox와의 역할 차이

- 버전·묘비: Redis에 도착한 옛 값의 저장을 거절한다.
- outbox: DB 변경과 함께 Redis에 반영할 일을 DB에 기록하고, 작업자가 실패 시 재시도하게 한다.
- CDC: DB 변경을 감지해서 무효화에 연결할 수 있다.

outbox의 하나의 DB 트랜잭션에 묶이는 것은 **상품 변경 + outbox 기록**이다. DB와 Redis가 동시에 변경되는 것은 아니어서 작업자의 반영 전까지 불일치 구간은 남는다.

outbox로 `DEL` 전달을 재시도해도, 그 뒤에 A가 옛 값을 재삽입하는 문제까지 자동으로 해결되지는 않는다. outbox를 사용한다고 Kafka가 반드시 필요한 것도 아니다. 작업자가 DB의 outbox를 조회해서 Redis를 직접 무효화할 수 있다.

## 남은 문제의 대응 방법

다음은 설계 방향을 설명한 것이며 현재 실습 코드에는 구현하지 않았다.

| 문제 | 대응 방법 | 추가로 고려할 점 |
|---|---|---|
| DB commit 후 묘비 기록 실패 | outbox에 반영 작업을 함께 기록하고 재시도하거나 CDC로 변경 감지 | 반영 전 불일치는 남으며 중복·역순 이벤트도 처리해야 함 |
| 버전 기준 만료·eviction | 가격과 버전 기준의 수명을 분리하고 기준을 별도로 보존 | 기준도 지우거나 eviction되면 같은 문제가 돌아옴. 계속 보존하면 메모리 비용 발생 |
| 유한한 시간 뒤 버전 기준을 안전하게 정리해야 함 | Redis에서 저장 권한의 유효성을 검사하는 lease 등의 별도 프로토콜 검토 | 일반 timeout만으로 충분하지 않음. 늦은 요청의 저장을 Redis가 거절해야 함 |
| 저장을 거절한 A가 옛 값을 응답 | 저장 거절 시 DB 재조회 검토 | 재조회 직후에도 변경될 수 있음. 재시도 횟수·기한과 요구하는 읽기 보장을 정의해야 함 |
| 다른 코드가 규칙을 우회 | 모든 관련 DB 변경에서 버전 증가, 모든 cache 저장에서 검사 적용 | 배치·관리 도구·직접 Redis 쓰기까지 점검 |

버전 기준을 별도 key로 분리하면 현재의 한 key Lua도 함께 바꿔야 한다. 가격 TTL과 버전 기준의 보존 기간을 구분할 수 있지만, 그 자체로 영구적인 안전을 보장하지는 않는다.

정확성이 필요한 업무 판단은 DB에서 수행하고, 그 판단에 필요한 DB 트랜잭션·조건부 갱신·락을 선택한다. cache를 유지하는 비용이 이득보다 크면 해당 조회를 cache에서 제외할 수 있다.

## 설계 선택

잠깐의 옛 값을 허용하는 조회는 기본 cache-aside + commit 후 `DEL` + TTL로 시작할 수 있다. TTL은 업무에서 허용하는 불일치 시간과 DB 부하를 기준으로 결정한다.

무효화 누락을 복구해야 하면 outbox·CDC를, 늦은 옛 값의 재삽입을 막아야 하면 버전·묘비와 보존 조건을 검토한다. 결제 가격 확정·재고 차감처럼 정확해야 하는 판단은 원본 DB에서 검증한다.

## 핵심 요약

버전·묘비 방식은 **Redis에 버전 기준이 남아 있고 모든 저장이 Lua 검사를 거치는 동안 더 낮은 버전으로 cache가 덮이는 것을 막는다.**

DB commit 후 묘비 기록 실패, 버전 기준의 만료·eviction, 이미 읽은 옛 값의 응답까지 해결하지는 못한다. 기본 방식이 어디서 깨지는지 구분하고, 필요한 보장에 맞춰 장치를 선택한다.
