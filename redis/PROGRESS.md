### ①-a 완료한 예측과 실습 기록

> 상품 1번은 DB에 가격 100, 버전 1로 들어 있고 캐시는 비어 있다.
> 1. 요청 A가 캐시 미스 → DB에서 (100, v1)을 읽고, 캐시에 쓰기 직전 멈춘다.
> 2. 그 사이 요청 B가 DB를 (200, v2)로 바꾸고 커밋한 다음 캐시를 DEL한다.
> 3. A가 재개해서 자기가 읽은 값을 캐시에 쓴다.
>
> Q1. 끝나면 캐시에는 뭐가 있고, 그 상태는 언제까지 가나? (TTL 60초)
> Q2. B의 순서를 "캐시 DEL → DB 갱신"으로 바꾸면 이 장면이 막히나?

정답(실행 확인함): Q1 캐시 = (100, v1), DB = (200, v2). TTL 60초가 끝나거나 다음 갱신이 DEL할 때까지 옛 값. Q2 안 막힘(A가 DB를 B 갱신 전에 읽은 경우 같은 장면, 오히려 DEL과 갱신 사이 읽기가 끼는 창이 하나 더 생김).
그다음 `uv run run.py 1a-race` 실행(고치기 전 stale 1, 빨강 정상) → 사용자가 결정 지점(읽기 쪽 HSET, 쓰기 쪽 DEL)을 고칠 방향 지시. 짚을 것: 버전 비교만 하고 DEL로 무효화하면 왜 여전히 깨지나(묘비 필요), `1a-crash`는 Redis로 못 막음(TTL 상한·CDC). 쓰기 쪽 버전은 `UPDATE ... RETURNING version`으로 받기(커밋 후 다시 SELECT하면 다른 쓰기와 섞임).

## 2026-11-06 진행
- 확인: `1a-race`에서 DB=(200,v2), cache=(100,v1), TTL=60. 수정 전 stale=1 재현.
- Q1·Q2: 옛 값 재삽입과 DEL 순서 변경의 한계를 정확히 예측. 락은 양쪽 경로가 같은 락을 지켜야 함을 설명만 함.
- Windows 출력은 `PYTHONIOENCODING=utf-8`로 실행. 회고 결론은 아직 기록하지 않음.
- 사용자 설명: 버전 비교로 stale 저장을 거절하는 목적 이해. cache-aside의 조회 채우기·변경 무효화, commit 후 사망과 재삽입의 차이를 설명함.
- 확인: 새 버전 `uv run run_versioned.py all`의 4개 시나리오 기대 일치. race는 cache_stored=False·stale=0, crash는 여전히 stale=1. 묘비 조회 후 v2 채우기, 역순 무효화 거절, 만료 상태에서 옛 값 저장 허용도 실행 확인. ruff 통과.
- 실무 연결(설명만): Redis 클라이언트의 Lua EVAL로 검사·저장 원자화. 묘비 TTL 60초는 실험값이며 무한 정지·eviction·commit 후 사망을 해결하지 않음.
- 사용자 설명 확인: read()의 stale 저장 거절과 update()의 묘비 기록 전 사망은 별도 문제임을 구분. Hash의 tomb, eval의 KEYS·ARGV, Lua의 검사·쓰기 원자성과 Spring RedisScript 관리 방식까지 질의·설명.
- 문서화: `CACHE-ASIDE.md`에 기본 문제·개선 범위·한계·남은 문제의 대응 방향·실습 결과 기록. outbox·CDC·별도 버전 보존·lease·재조회는 설명만 함.
