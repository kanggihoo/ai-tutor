# GoF 디자인 패턴: 23개 중 무엇을, 왜

GoF(Gang of Four) 23개 패턴을 **지금 기준으로 골라서** Java 코드로 빠르게 확인하며 배운다. 도메인은 `distsys/`와 같은 주문·결제다.

**고르는 기준**: "구체적인 변경 요구가 왔을 때 도움이 되고, 더 단순한 대안(조건문, 람다)과 비용을 비교할 수 있는가." 유명하거나 자주 들린다는 이유만으로 넣지 않는다. 뺀 것도 "쓸모없다"는 뜻이 아니라 **이 과목의 지금 문제와 거리가 멀다**는 뜻이다.

이 선별은 Claude와 Codex가 9턴 동안 토의해서 합의한 결과다(2026-11-03).

## 23개 지도

| 표시 | 뜻 |
|---|---|
| 🛠 실습 | 코드를 실행하고 고친다. `Check.java` 통과가 기준 |
| 👀 판독 | 짧은 코드를 보고 "왜 이 패턴인지" 이유를 한 줄로 말하면 통과 |
| ⏩ 빠른 점검 | 생성 패턴. 이미 설명할 수 있으면 건너뛴다 |
| ⛔ 제외 | 다루지 않는다. 아래에 이유와 다시 볼 조건 |

### 생성 (5) — 빠른 점검, 체크포인트 01
| 패턴 | 표시 | 이 과목에서 보는 장면 | 실무에서 |
|---|---|---|---|
| Builder | ⏩🛠 | 같은 `int` 인자(금액·포인트)가 나란히 있는 생성자에서 순서를 바꿔 넣는 실수 | `HttpRequest.newBuilder()`, `StringBuilder` |
| Prototype | ⏩🛠 | 장바구니 복제("다시 주문하기")에서 리스트를 공유해 원본이 바뀜 | `clone()` 대신 복사 생성자·`List.copyOf` |
| Singleton | ⏩🛠 | 전역 설정을 테스트가 바꿔서 다음 테스트가 깨짐 → 생성자로 주입 | Spring 빈 싱글톤은 컨테이너당 1개일 뿐, GoF 싱글톤이 아니다 |
| Factory Method | ⏩👀 | 단순 정적 팩토리(`of`)와 "하위 클래스가 무엇을 만들지 정함"을 구분 | `List.of`(정적 팩토리), `Iterable.iterator()` |
| Abstract Factory | ⏩👀 | "함께 바뀌는 제품군"(예: PG사마다 승인·환불 클라이언트 한 벌) | `DocumentBuilderFactory` |

### 구조 (7)
| 패턴 | 표시 | 이 과목에서 보는 장면 | 실무에서 |
|---|---|---|---|
| Adapter | 🛠 | 외부 PG SDK를 우리 `PaymentGateway` 인터페이스에 맞춤 | `InputStreamReader`, `Arrays.asList` |
| Decorator | 🛠 | 결제 호출에 로깅·재시도를 덧붙임 | `BufferedInputStream` |
| Proxy | 🛠 | 결제 조회에 캐시·권한 확인을 끼움 | `java.lang.reflect.Proxy`(Spring AOP의 원리) |
| Facade | 👀 | PG 호출 셋(인증·승인·영수증)을 하나로 묶음. Adapter와 어떻게 다른가 | 서비스 계층이 모두 Facade인 것은 아니다 |
| Composite | 👀 | 단일 할인과 "할인 묶음"이 같은 `apply(price)`를 가짐 | UI 트리, 파일 시스템 |

### 행위 (11)
| 패턴 | 표시 | 이 과목에서 보는 장면 | 실무에서 |
|---|---|---|---|
| Strategy | 🛠 | 결제 수단별 수수료 계산. 람다 버전과 비교 | `Comparator` |
| State | 🛠 | 주문 상태(생성 → 결제 → 취소) 전이. 금지 전이(취소 후 결제) 검사. enum/sealed + switch 버전과 비교 | 주문·결제 상태 머신 |
| Observer | 🛠 | 주문 완료 시 알림·포인트 적립이 구독 | 이벤트 리스너, `distsys/`의 이벤트 |
| Chain of Responsibility | 🛠 | 주문 검증 필터(재고 → 한도 → 차단 고객) | 서블릿 `Filter`, 미들웨어 |

## 왜 5개를 뺐나

| 패턴 | 하는 일 | 뺀 이유 | 다시 볼 때 |
|---|---|---|---|
| **Bridge** | 독립적으로 늘어나는 **두 변화 축**(예: 결제 수단 × 통화)을 상속 조합 폭발 없이 분리 | 이 과목 도메인에는 변하는 축이 하나뿐이라 필요한 장면을 만들 수 없다. 축이 하나일 때는 Strategy와 구분되지 않는다 | 두 축이 실제로 함께 늘어날 때. 예: JDBC(`DriverManager` ↔ 드라이버), SLF4J ↔ 로깅 구현체 |
| **Flyweight** | 같은 객체 수백만 개의 공통 상태를 공유해 메모리를 줄임 | 앱 코드에서 직접 만들 일이 드물다. 대부분 JVM·라이브러리가 대신한다(`Integer.valueOf` 캐시, 문자열 상수 풀) | 프로파일러가 같은 객체가 대량으로 메모리를 잡는다고 보여 줄 때(게임, 텍스트 편집기 글리프) |
| **Mediator** | 서로 직접 부르는 객체들의 그물을 중재자 하나로 모음 | Observer와 구분하는 판단 기준을 세우려면 별도 실습이 필요하다. 한 줄 설명으로 끝내면 오히려 Observer와 헷갈린다 | UI 폼 컴포넌트들이 서로의 상태를 바꾸는 코드, 채팅방·관제탑 구조 |
| **Visitor** | 고정된 타입 계층에 연산을 계속 추가 | 이 학습자의 우선 문제(결제·주문 변경 대응)와 거리가 멀다. Java 21+의 sealed + switch 패턴 매칭으로 더 짧게 풀리는 경우도 많지만, 항상 대체된다고 일반화하지는 않는다 | 컴파일러 AST, 문서 트리를 다룰 때. 라이브러리 API에서 만날 때(`javax.lang.model`, ASM) |
| **Interpreter** | 작은 언어의 문법을 클래스 계층으로 표현하고 해석 | 앱 개발에서 직접 만드는 일이 드물다. 정규식 엔진, SpEL, 파서 생성기처럼 라이브러리가 맡는다 | 직접 DSL이나 규칙 엔진을 만들 때 |

## 배우는 방식
- 체크포인트마다 **예측 → `java Check.java` 실행 → 1~5줄 수정 → 재실행 → 이유 설명 → 패턴 이름 공개, 이 지도에 체크**.
- 비슷하게 생긴 것끼리 묶는다. 감싸기(Adapter·Decorator·Proxy), 교체(Strategy·State), 요청 처리(Observer·CoR·Command). 구조가 같아도 의도가 다르다는 걸 비교한다.
- 묶음마다 **과용 리뷰** 1문제: 패턴을 과하게 쓴 AI 코드를 보고 유지·단순화·삭제 중 하나를 고른다. 구현 개수가 아니라 "이번 변경 요구에 비해 추가된 복잡성이 값어치를 하나"로 판단한다.
- 조건문이나 람다를 그대로 두는 것도 정답이 될 수 있다.
- 분류에 유일한 정답을 강요하지 않는다. 근거가 있으면 다른 분류도 인정한다(예: `Collections.unmodifiableList`는 Proxy인가 Decorator인가).
