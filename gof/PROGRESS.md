## 2026-11-03 학습 기록
- Builder: 인자 의미 명시와 유지보수 이점을 설명함. 좌표처럼 인자가 적어도 혼동이 잦으면 도입 근거가 있다는 의견. Lombok @Builder로 반복 구현 비용을 줄일 수 있음을 짚음.
- Prototype: 처음에는 새 Cart면 리스트도 독립적이라고 예상. 이후 참조 공유를 이해하고 새 리스트에 기존 원소를 넣는 수정을 스스로 제안함. 불변 String은 공유 가능하고 문자열 덧붙이기는 기존 문자열을 수정하지 않음을 이해함.
- Prototype 활용: 기존 주문·문서·설정 복제. 비싼 초기화 결과를 재사용할 수 있지만 복사가 항상 빠른 것은 아니며, 변경할 데이터는 독립적으로 복사해야 함을 설명.
- Singleton·Iterator: 이미 익숙하다는 사용자 요청으로 생략(검증 없음).
- Factory Method: 부모 공통 흐름에서 자식이 생성 방법을 정함. Spring DI로 충분한 결제 예제에는 필요성이 약하다는 사용자 지적. 상속 기반 라이브러리의 생성 확장 지점으로 설명(판독 검증 없음).
- Abstract Factory: 관련 객체의 생성을 묶고 팩토리를 교체하면 제품군이 함께 바뀌는 구조로 설명. 사용자는 관련 객체를 만드는 클래스로 이해(판독 검증 없음).
- Adapter: 외부 SDK를 우리 Payment 인터페이스에 연결하고 SDK 호출 변경을 어댑터에 모으는 구조를 사용자 스스로 설명함. Payment p = new VendorPaymentAdapter(...)로 사용함을 이해.
- Decorator: 같은 Payment를 구현하는 객체로 기존 Payment를 감싸 로깅 등 기능 추가. 같은 인터페이스 구현은 원래 객체 자리에 대입하고 여러 겹 조합하기 위한 것임을 설명.
- Python 연결: 함수를 받고 감싼 함수를 반환하는 고차 함수와 함수 데코레이터 비교. Python @ 문법 전체가 GoF Decorator를 뜻하지는 않음.
- Spring 연결: 공통 로깅은 AOP로 적용 가능. Spring AOP는 프록시 기반이며 Decorator와 동의어는 아님. 어노테이션은 정보, 리플렉션은 런타임 조사·호출 수단. @Override처럼 컴파일 시 처리하는 예외도 설명.
- Proxy: 권한 검사로 실제 결제 호출을 제한하는 코드를 제시했으나 응답 전 종료. 사용자 요청으로 다음 시간에 처음부터 다시 진행.

- (2026-11-03 2차) 복습: Adapter=외부 SDK 변경 흡수 중간다리, Decorator=기존 코드 유지하고 앞뒤 기능 추가로 정확히 답함. 보충: Adapter는 인터페이스 모양 변환도, Decorator는 여러 겹 쌓기 가능.
- Proxy는 완전 처음이라는 사용자 지적 → 실습 전에 개념부터(비서 비유, Decorator와 의도 비교, @Transactional·JPA 지연 로딩). **새 패턴은 개념 먼저, 실습은 그 다음.**
- 네트워크 프록시와 같은 아이디어(앞에서 받아 처리 후 진짜로 전달)라고 스스로 연결함. 질문: Spring 어노테이션 중 AOP와 리플렉션 처리 구분 → 기준 "호출 앞뒤에 끼어드나", 자기 호출(this.method())이 깨지면 프록시. @Valid(컨트롤러, 프록시 아님) vs @Validated(서비스, 프록시) 설명(설명만).
- 튜터 실수: 깨진 체크포인트 코드를 "일부러 틀린 것"이라고 밝히지 않고 보여 줘서 혼란과 불만. **깨진 코드는 처음부터 "버그 있는 버전"이라고 말한다.**
- Proxy 실습은 사용자 요청("다음")으로 생략. 정답만 알려 줌. `lab/02_wrapping/`은 ❌ 1개 그대로, 지도 체크 안 함.
- Facade: 개념(여러 호출 → 메서드 하나, Adapter와 대비) 설명 후 판독 질문 "repository.save() 하나만 위임하는 OrderService도 Facade인가?" (정답 방향: 단순화할 여러 호출이 없으니 Facade라 부를 근거 약함)

## 2026-11-07 학습 기록
- Proxy·Decorator 복습(대화): 사용자는 Proxy를 먼저 받아 작업 후 실제 객체에 전달하는 구조로, Decorator를 기존 로직을 유지하며 앞뒤에 기능을 추가하는 구조로 설명함. Decorator 목적은 정확함. Proxy는 실제 호출 여부·시점을 통제하며 호출하지 않을 수도 있다는 점을 보충함(설명만, 실행 없음).
- Facade(대화): 복잡한 원래 기능에서 사용하는 쪽에 필요한 기능을 간단하게 제공하는 래핑 클래스로 이해함. 사용자가 단일 메서드 위임도 Facade가 될 수 있음을 지적함. 튜터의 '여러 호출 필수' 설명을 정정: 호출 수가 아니라 감추는 복잡함과 사용 단순화가 판단 근거이며, 단순 위임 코드만으로는 근거가 약함.
- Facade 활용: 사용자가 SDK처럼 다른 사람이 쉽게·직관적으로 사용하도록 만드는 패턴으로 스스로 연결함. 내부 절차·의존성을 줄이는 것이 핵심이고 프로젝트 내부 모듈에도 적용 가능함을 보충함(대화 이해 확인, 코드 실행 없음). 감싸기 과용 리뷰는 아직 진행 전.
- 감싸기 과용 리뷰(대화 통과): '구현체가 하나뿐이므로 VendorPaymentAdapter를 제거하자'는 제안에, 사용자는 SDK 변경 대응을 위해 유지하되 API가 안정적이면 상황에 따라 판단해야 한다고 답함. 후속 답변에서 외부 모듈 의존을 Adapter에서 관리하는 유지보수 근거를 제시함. 튜터 보충: 수정이 없어지는 것이 아니라 변환·의존성 관련 수정을 경계 한곳에 모으며, 외부 모듈마다 무조건 Adapter가 필요한 것은 아님. 코드 실행 없음.
- 현재 이어갈 지점: 감싸기 과용 리뷰 통과. 다음은 03 Strategy 개념부터. 02 Proxy 코드 실습 실패는 여전히 미해결이며 감싸기 전체 완료로 간주하지 않음.
- Strategy(대화): 사용자는 단순 정책은 switch/if로 충분하다고 지적함. 튜터는 정책별 로직·의존성이 복잡해질 때 선택과 실행을 분리하는 이점을 설명함. VIP·쿠폰·행사 정책의 공통 DiscountPolicy 구현 예시를 제시함(예시만, 실행 검증 없음).
- Strategy 이해 확인: 사용자가 선택 인자로 switch 분기해 정책 객체로 라우팅하는 구조를 설명하고, 새 정책 클래스와 선택 분기 추가로 확장할 수 있음을 스스로 도출함. 추가 인자·switch는 필수가 아니며 생성자 주입도 가능함을 보충함. 정책 추가 시 기존 정책과 계산기는 유지되지만 클래스·탐색 비용이 늘어 단순한 경우 switch 유지가 합리적임을 설명함.
- 다음 대화: Strategy의 간단한 정책을 Java 람다로 표현하기. 03 실습 폴더는 아직 준비하지 않았으며 실행 체크포인트·README 통과 체크도 하지 않음.
- Strategy 람다 보충: 사용자는 복잡한 정책을 람다로 표현할 이유가 없다고 지적함. 튜터는 불필요한 양자택일 질문을 인정하고, 람다는 간단한 정책의 선택적 표현일 뿐임을 정정함. 이후 사용자 요청으로 다음 개념으로 진행.
- State(대화): 사용자가 현재 상태에 따른 허용 행동·전이로 이해함. HTTP 무상태성과 서버의 도메인 상태 저장을 구분하고, FE가 보낸 상태 대신 서버의 주문 상태를 기준으로 판단함을 설명함. 사용자는 Order 자체가 상태·규칙을 관리하는 캡슐화와 DDD 연결을 제시함. State 객체 위임도 Order의 외부 API 안에서 구현 가능하며, 작은 상태 집합은 enum + 조건문이 충분하다고 설명함. 실행 검증 없음.
- Template Method(대화): 공통 흐름은 부모에서 정의하고 세부 단계는 자식에서 구현하는 상속 활용으로 사용자가 설명함. 부모의 고정된 흐름이 자식의 단계를 호출하는 구조가 핵심이며 단순 상속 전체와는 구분됨을 보충함. 실행 검증 없음.
- Composite(대화 이해 확인): 파일·폴더 size() 예시로 설명함. 사용자는 개별/묶음 구분 없이 같은 인터페이스의 메서드를 호출하고 각 내부 구현이 값을 반환한다고 설명함. 튜터는 단순 공통 인터페이스만이 아니라 묶음이 같은 인터페이스의 자식을 담는 재귀 구조가 핵심임을 보충함. - Observer(대화 이해 확인): 사용자가 SSE·WebSocket의 구독과 연결함. 튜터는 Observer는 구독·통지 구조, SSE·WebSocket은 전송 방식이며 함께 사용 가능하지만 동일 개념은 아니라고 구분함. 사용자는 listeners에 등록 후 순회하며 모든 구독 객체에 알림을 보내는 구조를 정확히 설명함. 같은 알림 메서드를 호출하되 각 listener의 실제 작업은 다를 수 있음을 보충함. 직접 호출 예시는 동기이며 Observer 자체가 비동기를 보장하지 않음을 설명함. 실행 검증 없음.

- Chain of Responsibility(대화 이해 확인): 순서대로 연결한 검증 처리자가 다음 단계에 넘기거나 중단하는 주문 예시를 설명함. 사용자가 Spring Security filter chain·Servlet Filter·다른 언어의 next() middleware와 스스로 연결함. 튜터는 다음 단계 위임과 중단 가능성이 핵심임을 확인하고 Servlet Filter 및 Express 형태의 축약 예시를 제시함(실행 없음). 사용자 요청으로 Command로 진행.
- Command(대화 설명): 실행할 요청을 객체로 포장하고 저장 후 실행하는 예시를 제시함. 사용자는 단순 객체 저장·호출과 무엇이 특별한지 질문함. 튜터는 단일 작업은 데이터 목록으로 충분하며, 서로 다른 작업을 동일 execute()로 실행해 작업 등록과 실행 관리를 분리할 때 이점이 있다고 설명함. 최초 실행 예측 질문은 답변받지 않았으므로 통과로 간주하지 않음.
