# Kafka offset: 두 그룹의 위치 변화 따라가기

이 문서는 2026-11-07 대화에서 헷갈렸던 지점을 복습하기 위한 설명 자료다. 아래 표는 개념 시나리오이며, 두 그룹을 실제로 실행해 얻은 로그는 아니다.

## 먼저 구분할 세 가지

| 이름 | 의미 | 어디에 속하거나 저장되는가 |
|---|---|---|
| 메시지 offset | partition 안에서 메시지에 붙은 번호 | 해당 topic의 해당 partition |
| 현재 위치 | 실행 중인 consumer가 다음에 읽을 offset | consumer 쪽 메모리, 할당된 partition별 |
| 커밋 위치 | 재시작·재할당 때 이어 읽을 offset | Kafka에 consumer group·topic·partition 조합별로 저장 |

메시지 번호가 그룹마다 새로 붙는 것은 아니다. 같은 메시지 목록을 읽으면서 각 그룹이 자기 진행 위치를 따로 저장한다.

"위치가 2개"라는 말은 P0 전체에 공용 위치가 두 개라는 뜻이 아니다. 아래 예시에는 A의 현재 위치, X의 현재 위치, 결제 그룹의 커밋 위치, 통계 그룹의 커밋 위치가 있어 총 4개다.

## 고정된 등장인물

```text
Kafka: 주문 topic
  P0: [offset 0] [offset 1] [offset 2] [offset 3] …
          │
          ├───────────────────────┐
          ▼                       ▼
  ┌─ 결제 consumer group ─┐  ┌─ 통계 consumer group ─┐
  │ consumer A           │  │ consumer X           │
  │ 주문마다 결제 저장   │  │ 주문마다 통계 갱신   │
  └──────────────────────┘  └──────────────────────┘
```

A와 X는 다른 그룹이다. 메시지를 하나씩 나눠 받는 관계가 아니라, 각각 0번부터 같은 메시지를 모두 읽는다. X가 빨리 진행해도 A의 위치는 바뀌지 않는다.

설명 조건:

- 자동 오프셋 커밋은 꺼져 있다.
- `poll()` 한 번에 메시지 하나를 받으며, 별도 prefetch 세부사항은 생략한다.
- 시작할 때 두 그룹의 P0 커밋 위치는 모두 0이다.
- 표의 모든 위치는 **다음에 읽을 메시지 번호**다.

## 시나리오: X가 먼저 끝내고 A가 중간에 죽는 경우

### ① 처음 시작

| Consumer / 그룹 | 현재 위치: consumer 메모리 | 커밋 위치: Kafka |
|---|---:|---:|
| A / 결제 | 0 | 0 |
| X / 통계 | 0 | 0 |

두 consumer 모두 다음에 offset 0을 받는다.

### ② A가 poll로 offset 0 수신, 결제는 아직 처리 중

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | **1** | 0 |
| X / 통계 | 0 | 0 |

A가 메시지를 받았으므로 A의 현재 위치만 1로 이동한다. 수신은 결제 성공을 뜻하지 않으므로 커밋 위치는 그대로다.

### ③ X도 poll로 offset 0 수신

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | 1 | 0 |
| X / 통계 | **1** | 0 |

X는 자기 현재 위치로 읽으므로 A가 이미 받은 0번을 똑같이 받는다.

### ④ X가 0번 통계 처리를 완료하고 위치 1 커밋

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | 1 | 0 |
| X / 통계 | 1 | **1** |

X가 Kafka에 저장한 것은 `통계 그룹 / 주문 topic / P0 → 1`이다. 결제 그룹의 커밋 위치에는 영향이 없다.

### ⑤ X가 offset 1을 수신

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | 1 | 0 |
| X / 통계 | **2** | 1 |

X는 1번을 받았지만 아직 처리 완료를 커밋하지 않았다.

### ⑥ X가 1번 통계 처리도 완료하고 위치 2 커밋

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | 1 | 0 |
| X / 통계 | 2 | **2** |

통계 그룹은 0·1번까지 끝났다. 결제 그룹은 여전히 0번을 처리 중이다. 두 그룹의 속도가 달라도 된다.

### ⑦ A가 DB 커밋 후, Kafka 오프셋 커밋 전에 죽음

A는 payments DB에서 `processed_events`의 inbox 기록과 결제 INSERT를 한 트랜잭션으로 커밋했다. 그러나 Kafka에 위치 1을 저장하기 전에 프로세스가 죽었다.

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---|---:|
| A / 결제 | **프로세스 종료로 사라짐** | 0 |
| X / 통계 | 2 | 2 |

payments DB에는 A가 처리한 0번 이벤트의 기록과 결제가 남아 있다. Kafka의 결제 그룹 커밋 위치는 여전히 0이다.

### ⑧ A 재시작: 결제 그룹의 커밋 위치로 복원

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | **0** | 0 |
| X / 통계 | 2 | 2 |

A는 `결제 그룹 / 주문 topic / P0`의 위치 0을 사용한다. 통계 그룹이 저장한 위치 2는 사용하지 않는다.

같은 결제 그룹의 새 consumer B가 P0을 넘겨받는 경우에도 결제 그룹의 커밋 위치를 사용한다. 커밋 위치는 A 개인의 기록이 아니다.

### ⑨ A가 offset 0 재수신

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | **1** | 0 |
| X / 통계 | 2 | 2 |

payments DB의 inbox에 같은 `event_id`가 있다. `INSERT … ON CONFLICT DO NOTHING`은 0행을 삽입하며, 우리 코드가 이를 검사해 결제 INSERT를 건너뛴다. DB가 저절로 프로그램의 다음 작업을 생략하는 것은 아니다.

### ⑩ 이미 처리된 이벤트임을 확인하고 A가 위치 1 커밋

| Consumer / 그룹 | 현재 위치 | 커밋 위치 |
|---|---:|---:|
| A / 결제 | 1 | **1** |
| X / 통계 | 2 | 2 |

결제를 새로 만들지는 않았지만, 이 이벤트의 결제가 이미 끝났음을 확인했다. 위치 1을 저장했으므로 이후 재시작해도 0번부터 다시 읽지 않는다.

## 커밋을 전혀 안 해도 다음 poll은 진행하는가?

자동 커밋이 꺼져 있고, A가 계속 살아 있으며 P0 재할당이나 명시적인 위치 변경도 없다면 진행한다.

```text
동작                           A 현재 위치   결제 그룹 커밋 위치
시작                               0                 0
0번 수신·처리                      1                 0
1번 수신·처리                      2                 0
2번 수신·처리                      3                 0
```

오프셋 커밋은 다음 메시지를 받기 위한 허가가 아니다. 복구할 때 사용할 위치를 저장한다. 위 상태에서 재시작하면 저장된 위치 0부터 다시 읽는다. 실제 장기 운영에서는 해당 데이터가 topic에 보존되어 있어야 재수신할 수 있다.

`c.commit(message=msg, asynchronous=False)`는 해당 메시지의 `offset + 1`을 저장하고 응답을 기다린다. 커밋 호출 횟수만큼 기존 위치를 무조건 1씩 올리는 연산이 아니다.

## 같은 그룹에 consumer가 여러 개라면?

```text
주문 topic            결제 consumer group
P0 ─────────────────→ A
P1 ─────────────────→ B
P2 ─────────────────→ B
```

한 그룹 안에서 한 partition은 한 시점에 consumer 한 개가 담당한다. consumer 한 개는 여러 partition을 맡을 수 있다. 따라서 P0의 0번은 A, 1번은 B에게 나눠 주는 구조가 아니다.

다른 통계 그룹의 X가 P0을 읽는 것은 가능하다. 이때 결제 그룹과 통계 그룹의 P0 커밋 위치는 별도다. P1·P2도 각각 그룹별 커밋 위치를 가진다.

## 실습에서 지켜야 할 처리 순서

```text
poll
  → payments DB 트랜잭션: inbox INSERT + 결제 INSERT
  → DB 커밋 성공
  → Kafka 오프셋 커밋
```

DB 처리 실패 시에는 롤백하고 해당 메시지를 재시도하거나 소비자를 종료한다. 실패한 메시지를 둔 채 다음 메시지를 처리하고 더 앞선 위치를 커밋하면 안 된다.

```text
offset 0: 처리 실패
offset 1: 처리 성공 → 위치 2 커밋
재시작: 2부터 읽음 → 실패한 0을 건너뜀
```

consumer 내부 worker로 병렬 처리하는 경우에도 같은 위험이 있다. worker별로 각자 커밋하지 않고, partition별로 앞에서부터 빠짐없이 완료된 경계까지만 커밋해야 한다. 우리 실습은 메시지를 순차 처리하므로 내부 worker의 완료 순서 역전은 다루지 않는다.

## 복습 질문

1. X가 위치 2를 커밋했을 때 A의 현재 위치와 커밋 위치가 바뀌는가?
2. A가 0번을 받은 뒤 커밋 없이 계속 실행하면 다음 poll은 무엇을 받는가? 같은 상태에서 재시작하면 무엇을 받는가?
3. 결제를 DB에 커밋했지만 오프셋 커밋 전에 죽었다면, 재전달된 이벤트의 이중 결제를 무엇이 막는가?
4. 중복 이벤트를 건너뛴 뒤에도 오프셋을 커밋하는 이유는 무엇인가?
